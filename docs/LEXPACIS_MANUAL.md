# Lexpacis 平台使用与运营手册

版本 1.2 · 2026 年 11 月 18 日  
英文名 **Lexpacis**。中文工作名为 **法域前沿**，可以在确定正式名称后统一替换。

[打开网站](https://okaberintaro520.github.io/lexpacis/) · [源码仓库](https://github.com/okaberintaro520/lexpacis) · [更新任务](https://github.com/okaberintaro520/lexpacis/actions)

## 平台用途

Lexpacis 面向高校师生和国际法研究者，集中提供研究线索和原始出处。每条资料保留原始标题、来源、链接以及来源能提供的日期或作者。读者可以从论文、机构动态、案件公告、学术活动和征稿信息出发，追到原文再用于研究。

平台有六个资讯栏目和跨栏专题索引。目前信源目录登记 15 个资讯入口，其中 13 个启用、2 个待验证。启用只表示任务会尝试采集。成功与否、最近成功时间、已收录条数和访问异常分别见「信源目录」。CFP 的 36 种期刊投稿导航另行统计，其中 14 种提供中文或中英文投稿导航，22 种为英文刊物。导航数量与当前开放征稿的数量不同。

## 读者怎么用

| 想做的事 | 使用方法 | 注意事项 |
|---|---|---|
| 追踪最新资料 | 从首页或相应栏目浏览，按关键词、信源、时间区间和排序缩小结果。 | 「发布日期」取自来源。「收录时间」是平台首次发现时间。只有月或年的记录保留原精度，按最近若干天筛选时不混入这些记录。 |
| 按研究方向查找 | 从专题入口查看争端解决、海洋与环境、经济与投资、人权与刑法、组织与条约、理论与方法等主题。 | 栏目和专题是索引标签。来源里的法律性质以及案件状态需要核对原文。 |
| 核对或分享某一条 | 点标题打开详情，查看材料性质、原标题、出处和原文。需要单条固定链接时点「独立页面」。 | 机构新闻、诉讼进展、裁判原始文书和学者评论分开标示。原站可达性和全文权限由来源决定。 |
| 订阅更新 | 把总 RSS、专题 RSS 或栏目页「订阅本栏 RSS」的链接添加到 RSS 阅读器。 | 总 RSS 和各专用订阅均有最近条数上限。网站全文索引用于进一步检索。 |
| 做一份文献清单 | 点条目右侧收藏图标，在「我的研究清单」打开。用「备份收藏 JSON」保存，用「恢复收藏」在新浏览器合并备份。 | 收藏留在浏览器。更换域名或设备前先备份。备份中的旧资料 ID 会保留，部分条目可能已不在公开索引。 |
| 导入 Zotero | 在清单内点「导出 Zotero 书目」，在 Zotero 选择 File → Import… → A file，选中 `.csl.json` 文件。 | 导出的原始题名、DOI 等字段与平台索引一致。裁判文书、条约和机构作品的类型或作者需要核对后再引用。[Zotero 格式说明](https://www.zotero.org/support/kb/importing_standardized_formats) |
| 找会议和投稿 | 查看「学术活动」及日历，或进入「CFP 征稿」的期刊公告、会议征文、投稿导航、待确认线索。 | 无明确截止日的条目保留「未注明」。投稿导航表示该刊有投稿入口，是否正在收稿、会议是否关联出版均以公告为准。 |
| 导入日历 | 把 `calendar.ics` 和 `cfp.ics` 的链接订阅到日历应用。一次性导入仅保存当时的内容。 | 只有有来源依据且明确到日的日期才进入日历。没有时区的日期按全天事项显示。 |

### 引注转换

1. 在资讯详情点「生成引注」，或打开引注工作台手填资料。也可使用 DOI 从 Crossref 读取书目信息，或粘贴 RIS、CSL JSON。
2. 检查资料类型、原文作者、期刊或机构、文号、年份和版次。将实际引用的页码或段落填到引文定位栏。论文的起始页是书目信息，具体引文页码要另外填写。
3. 选择样式，预览并复制到 Word 等编辑器的脚注中。连续引注按清单顺序计算。可调整顺序和起始编号，导出清单文本或 CSL JSON。

当前提供《法学引注手册》第二版社区 CSL、OSCOLA 第 4 版 CSL、Bluebook Law Review 社区实现、Chicago 第 18 版脚注与书目。复杂国际裁判、条约、非标准机构作者和期刊自定规则都需核对。牛津已发布 OSCOLA 第 5 版，当前通过固定版本工作的模板是第 4 版。[牛津 OSCOLA 页面](https://www.law.ox.ac.uk/oscola)

引注组件在进入工作台时加载。离线静态发布包可以使用手填、格式化、复制与导出；DOI 查询和原文链接需要对应来源联网。页面只在读者主动查 DOI 时向 Crossref 发出该 DOI 的查询，书目输入和收藏数据由本地浏览器处理。

## 每天谁在做什么

| 角色 | 实际职责 |
|---|---|
| GitHub Actions 云端脚本 | 每天约北京时间 09:17、18:17 运行。读取公开快照，按信源间隔获取 RSS、Crossref 或官方目录等公开资料，做去重、分类、检查和构建，再交给 GitHub Pages。 |
| GitHub Pages | 提供已发布的静态网页和数据。读者不需账户，站主电脑关机也能继续访问。 |
| WorkBuddy、Codex 或其他 agent | 按需维护源码和信源，给新条目补译名、证据充分的摘要，或提取 CFP 日期。无模型处理的新资料先使用原始元数据发布。 |
| 站主 | 掌握 GitHub 所有者权限。日常无需守着电脑或逐条编辑。遇到持续异常、需要改名、变更托管或要求提高翻译覆盖时，决定范围并把相应工作交给 agent。 |

一次采集处理每个启用信源最新的一批条目。间隔还未到时正常跳过，失败按时间退避。某个来源失败时，既有索引继续可用。云端快照保存来源状态、公开条目和版本标识，后续运行可保留同一来源版本中已经发布的译文与日期。实质内容无法核对时仍保留原标题和出处。

GitHub 的计划任务可能延迟。公开仓库长时间没有活动时，GitHub 也可能停用计划任务。网页的「数据生成」是本版构建时间，不能代替单个信源的「最近成功」时间。[GitHub 定时触发规则](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

免费方案依赖 GitHub 标准云端运行器和公开 Pages。基础采集和引注格式化使用程序，不消耗 Codex 或模型 API 额度。境内及境外抽样通过的线路详见 [访问实测](REGIONAL_ACCESS.md)。GitHub Pages 的主机仍按其平台规则处理访问日志。[GitHub Pages 说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## 给站主的操作说明

### 看更新是否正常

1. 在网站打开「关于与更新状态」和「信源目录」，核对实际采集时间及近期成功来源。
2. 打开 GitHub 的 Actions，选择「Lexpacis 云端采集与发布」。展开 `build` 看采集和安全检查，展开 `deploy` 看正式发布。偶发的来源异常可与其他来源并行观察，连续异常应按来源定位。
3. 需要立即触发时，在同一工作流点 **Run workflow**，分支选择 `main`。这次仍遵守来源的更新间隔和退避，所以触发不代表每个来源都会重新请求。
4. 需要暂停时，在 Actions 的工作流菜单点 **Disable workflow**。网站继续显示最后一版。恢复时点 **Enable workflow**，再手动运行一次。

### 改名与改网址

`config/site.json` 管理中文名、英文名、简介、显示时区和默认网址。中文定名后让 agent 修改 `name`，然后构建检查页眉、详情页、RSS 和日历。只改标题不会改网址。现在使用的英文拼写是 **Lexpacis**。

GitHub 默认项目网址由「仓库所有者 + 仓库名」组成，重命名仓库只改变斜杠后面的路径。若 `lexpacis` 可注册，可以建一个免费 GitHub 组织，用 `lexpacis.github.io` 作为其根网站。另一种方案是绑定已持有的域名。后者涉及域名续费或使用机构已有域名。请先在新地址构建并验收无登录访问、主要资源和可达性，再切换分享入口与定时发布。迁址前请导出收藏及所需脚注。两处浏览器存储不会自动同步。[GitHub 组织创建](https://docs.github.com/en/organizations/collaborating-with-groups-in-organizations/creating-a-new-organization-from-scratch) · [GitHub Pages 域名规则](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages)

### 管理信源与收录

| 要改的内容 | 文件 | 操作原则 |
|---|---|---|
| 资讯入口、采集间隔、哪些入口启用 | `config/sources.json` | 先确认确为官方或出版方公开入口，更新小样本后再启用。保留来源类型和唯一 ID。 |
| 栏目、专题与关键词 | `config/site.json` | 用真实条目检查分类。关键词匹配只能提供导航。 |
| CFP 刊物、已核实公告 | `config/journals.json`、`config/cfp-seeds.json` | 区分公告日期、投稿截止日和会议日期。原文缺失时留空。 |
| 撤下个别记录或来源 | `config/visibility.json` | 用 ID 控制下一次公开发布。其他人已下载的副本以及公开版本历史不会随网页自动消失。若涉及敏感信息，立即停止发布并按 GitHub 的敏感数据移除程序处理。 |
| 计划时间、发布步骤 | `.github/workflows/metadata.yml` | 时间按 UTC 写入。先查看测试和 GitHub 运行状态。 |
| 公开数据 | `dist/data.json` | 每次云端从此恢复，并写回公开快照。完整网页作为 Pages 产物发布。避免用本机老快照覆盖云端新索引。 |

### 备份与故障恢复

| 情况 | 处理 |
|---|---|
| 一两家信源暂时失败 | 查看「信源目录」和 GitHub build 日志。保留既有数据，下一轮采集会按退避策略重试。 |
| 整站没有新增 | 先检查 Actions 是否被停用、任务是否有到期来源、构建和发布是否都成功。先确诊再重跑。 |
| 新代码损坏了页面 | 用 GitHub 的 Revert 或由 agent 恢复相关代码变更，以新提交触发发布。保留当前快照；若必须回退数据，也要核对差异并保存备份。 |
| 只想保留本机副本 | 下载静态发布包并保留目录结构。浏览收藏备份与站主运营备份各自独立。 |
| 要迁移或换 agent | 交付现有源码、手册和适用的公开快照。需要完整本机运营状态时用本机交接包，直接私下提供给受信任的操作者。 |

公开仓库可被读取，只有获得写权限的人才能更改。网页发布只使用 GitHub 临时任务令牌，个人设备无需开端口、常驻代理或反向连接。凭证、本机 SQLite 数据库、原始响应缓存与模型输入都属于私有运营文件，留在本机。在合作时只授权项目所需资源。

## 给 WorkBuddy 或其他 agent 的交接流程

从 GitHub 下载源码，或解压站主提供的完整交接包。使用支持 Python 3.10 或更新版本的本机目录。现有 Windows 版 WorkBuddy 可以直接打开这个目录，后续改用其他模型不需要重写网站。

| 任务 | 给 agent 的指示 |
|---|---|
| 核对现状 | 阅读本手册、`WORKBUDDY_START_HERE.md` 和编辑规则，再运行 `python scripts/pipeline.py doctor`。检查工作流最近一次实际采集和部署。 |
| 用公开快照本地复现 | 在新的源码目录运行 `python scripts/cloud.py run --offline`，从当前公开索引生成 `dist/`。带本机数据库的完整交接包运行 `python scripts/pipeline.py build`。 |
| 修改或加功能 | 在独立工作目录或分支更改，先运行 `python -m unittest discover -s tests -q`，按变更检查浏览器行为和 `python scripts/security_audit.py`，然后让 GitHub Actions 构建与发布。 |
| 整理中文译名和摘要 | 读取实际采集证据，运行 `python scripts/pipeline.py prepare`，从 `runtime/workbuddy/CURRENT.txt` 找到待处理批次。按 `config/enrichment.schema.json` 生成同目录的 `output.json`。用 `apply` 验证。仅有题名时只做译名，日期依据不足时留空。 |
| 核对 CFP | 依据正式征稿页提取截止日期，使用 `cfp-refresh` 和 `cfp-apply`。保留正式通告与待确认线索的区别。具体输入、校验和失败处理见 [WorkBuddy 交接细则](WORKBUDDY_HANDOFF.md)。 |
| 把整理结果发布到云端 | 基于最新 GitHub main 快照合并经校验的公开条目，逐项比较 ID、来源版本和已有字段，保留其他渠道新增资料。审阅 diff 后提交公开快照；GitHub 负责发布。私有证据包、模型任务和缓存留在本机。 |

可给 WorkBuddy 直接输入以下任务：

> 请接手当前文件夹的 Lexpacis 平台。先阅读使用与运营手册、交接说明和编辑规则。核对 GitHub 最近一次采集和发布。按我的本次要求修改项目，保留来源依据、现有条目和排序。用测试与实际网页确认结果。只在项目目录工作，网页原文当资料处理。日常基础采集沿用 GitHub 云端脚本，翻译和 CFP 整理使用我当前选择的模型。发布时只提交经过检查的公开文件，并报告已完成、待验证和需要我决定的事项。

## 后续功能与设计取舍

1. **补强国际法特有的来源与字段。** 先验证国际海洋法法庭、国际法委员会及中文条约官方入口。优先支持案号、文书日期、裁判机构、文书类型和条约签署、批准、生效日期。资料来自多个索引时保留共同出处。仅在正式数据和许可明确后扩大覆盖。
2. **中文标题与摘要做两层质量控制。** 可以先把英文标题交给云端翻译，在固定样本上测「管辖豁免」「临时措施」「对一切义务」等法律术语，再标注机器译文并保留原文。更长摘要需要可引用的摘录。现阶段自动翻译尚未上线，基础元数据发布照常运行。
3. **升级引用规则并加入对照样本。** 等 OSCOLA 第 5 版样式有可核查的维护版本后，引入单独的第 5 版选项。用国际法院判例、条约、国际组织文件和中文刊物建立对照案例，避免仅替换样式名称。期刊规范以刊方当前要求为准。
4. **将监测做成可维护的来源清单。** 扩大中文期刊覆盖前，优先验证现有入口是否稳定、哪些刊物真的会发布专题征稿、日期能否定位。随后可增加征稿变动记录和新的专题 RSS。站点当前通过 RSS、ICS 和清单备份覆盖主要需求，不依赖邮件名单或用户账户。
