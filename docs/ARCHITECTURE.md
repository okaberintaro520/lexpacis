# 架构与 AIHOT 参考取舍

## 为什么没有原样部署 AIHOT

研究参考仓库：https://github.com/KKKKhazix/AIHOT

本会话调研时审阅的提交：`4c6e9e17068d16ef883124f51acd0e5aeb265ec2`。它提供自动采集、模型加工、任务队列、前端展示等思路。用户随后明确要求：减少 Codex 消耗、尽量不新增账单，并可交给 WorkBuddy 使用其他模型运营。

因此，本版保留自动采集、可配置来源、去重、语言整理、分模块展示与失败恢复的思路，采用独立的 Python 标准库任务程序和静态网页实现。没有移植 AIHOT 的源码，也不宣称是其官方分支。

不采用持续在线的 SSR + PostgreSQL + 队列服务，原因是第一版的读取场景不需要持续付费服务器。SQLite 承担本机持久化；JSON 文件承担模型交接；静态站点承担公开展示。

## 运行链

```text
公开 RSS / Crossref / 官方目录
            ↓
collect：最短间隔、条件请求、失败退避
            ↓
SQLite：来源、条目、版本、任务、证据
            ↓
prepare：受限批次 input.json
            ↓
WorkBuddy + 所选模型 → output.json
            ↓
apply：字段、版本、证据片段、日期、身份检查
            ↓
build：同一可见数据集 → HTML / RSS / ICS / JSON
            ↓
publish：本地 ZIP 或已配置 Cloudflare Pages
```

模型未运行时，collect → build → publish 仍成立，页面保留元数据。网页访问从不调用模型。

## 幂等与持久化

- DOI 优先作为标识；无 DOI 时使用规范化 URL 的哈希，移除常见跟踪参数。
- 相同资料重复采集只更新来源观察；不重复创建条目。不同入口的同一 DOI 记录来源关联。
- 内容哈希包含标题、日期、作者、证据与书目信息；原始依据变化后，旧摘要停止公开。
- 每个来源独立事务，失败不清空既有资料。HTTP 304 保留数据并记录本次成功。
- 准备中的同一批次复用；证据过期时自动淘汰并准备新批次。
- 已接收条目不重复接收；拒绝输出记录原因。成功条目和失败条目可同时存在。
- 排他锁阻止同一目录并发更新。数据库采用 WAL；交接备份通过 SQLite backup API 生成一致快照。
- 发布目录先在暂存目录构建，再切换；保留一个本地上一版本。详情、列表、RSS、日历与 JSON 使用同一可见性过滤。
- 本版不提供数据库、远程发布、外部客户端之间的分布式事务；上传失败保留本地发布包，下一次重试。

## 未承诺的能力

- 所有国际法文献和所有判例的完整覆盖。
- 仅凭字符串检查就证明法律语义正确。
- 从任意第三方网页自动发现并可靠解析全部日期。
- 永久无需处理登录失效、来源结构变化或磁盘故障。
- WorkBuddy 账户接入、实际周期任务和用户 Cloudflare 账户发布已经完成。

这些是第一版的实际边界，不需要通过每日逐条人工审核来维持基本更新。
